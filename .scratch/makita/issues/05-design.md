# 05 design: the task and its Thread, comment only

Ticket: `05-la-tarea-y-su-thread-solo-comentar.md`. Spec: `../spec.md` («La tarea y su Thread», «Atribución», «Amenazas de prompt injection», «Seguir la conversación» — loop guard). Builds on 04: a `queued` event becomes a task.

## What changes

- **Migration `167_MakitaTasks`**: `makita_tasks` with every column of the spec (`task_id` `mkt_<24 hex>`, `config_id`, `space_id`, `project_id`, `host`, `repo`, `number`, `kind`, `thread_id`, `caller_github_id`, `caller_login`, `state`, `branch`, `base_branch`, `head_sha`, `pr_number`, `pending_push_json`, `approved_through`, `last_push_at`, `landed_sha`, `ci_fix_attempts`, `replies_without_person`, `failure`, `created_at`, `updated_at`), `CHECK` on `kind` and `state`, a unique index on `thread_id`, and `UNIQUE (host, repo, number) WHERE state NOT IN ('done', 'stopped', 'failed')`: one live task per issue.
- **The seam for 06 and 07**: `makitaRows.makitaTaskOfThread(sql, threadId)` → `{ taskId, configId, spaceId, state, createdBy }` or none, one indexed read. The gateway (06: 403 when paused or stopped; 07: `makita_config_id` on usage), `EffectiveVaults` and the MCP door read it. A Thread is Makita's exactly when a task row names it; the row is written **before** the Thread is created, so no turn of it ever runs unmarked.
- **`makita/MakitaTasks.ts`** (the only writer of `makita_tasks`), run by the Scheduler right after the intake's pass (`makita-intake`): for each `queued` event:
  1. **Checks**, read now: Makita not paused (global nor configuration); the configuration's Space open; its creator active (`SpaceDirectory.isActive`), still in the Space and with `makita.use` there (`AccessPolicy`, as 02); the AI account still in `AllowedAiAccounts.for(creator, Space)`, not `direct`, accepted by `chooseAiAccount`; the issue (read again with Makita's token) open and not locked; the configuration's Project for that repository still there. A creator-side failure pauses the configuration with its reason (`creator-disabled`, `creator-left`, `permission-revoked`, audited as the system's pause) — the conservative half of ticket 17's table. Every failure leaves the event `ignored-paused` (Makita, the creator or the Space) or `ignored-no-config` (AI account, issue, Project) with the reason in `detail`, so the activity says it.
  2. **One transaction**: the task row (`running`, the caller from the event, `thread_id` fixed in advance: a UUID derived from the event key) and the event's `task_id`. A live task for the issue already (the unique index): the event becomes `ignored-no-config` / `task-open`.
  3. **The Thread**, through `ThreadLaunchService.launch` exactly as `ScheduledTaskService.runTask`: `CommandActor.actAsResolved({ _tag: "User", userId: creator })`, `ownerUserId` the creator, the configuration's Space, `CommandId` `makita:<event_key>` and `MessageId` `makita-message:<event_key>` (a retry after a restart replays nothing), title `Makita: <repo>#<n> <issue title>` (one line, 120 characters), the configuration's `ModelSelection`, `full-access` inside the Sandbox, workspace `root` (see «Deviations»). Then the event becomes `started` and Makita comments «On it. I'll report back here.» (no link to the Hub). A failed launch: the task `failed` with the reason, the event `started` (it did start), no comment. A crash between the row and the launch: the event is still `queued` with its `task_id`, and the next pass launches again with the same ids.
  4. Audit `makita.task.start` (`system`; `repo`, `number`, `trigger: label`, `caller`: the GitHub login).
- **Placement fixed to «Where it works»**: `ThreadLaunchInput.placement: "space-work"` → `EnvironmentRegistry.chooseForThread` skips a requested machine and the Project's preference and places the Thread where the Space's work runs: its Sandbox (the Hub machine only while the Hub runs agents itself, as for any Thread nobody placed). Never a personal or lent machine, never the caller's or the Project's choice. **Moving** a Makita Thread (`thread.move`) is refused: it stays where its configuration says it works.
- **What the agent of a Makita Thread never gets**:
  - Vault values, workload identity tokens included: `EffectiveVaults` answers an empty set for a Makita Thread (so `SecretDelivery` delivers nothing and signs nothing).
  - Tools outside the allow-list: the MCP door marks the call's scope `makita` (one read of `makita_tasks` by Thread) and an `McpServer.visibility` gate on every registration hides and refuses everything but `makita_read_issue`, `makita_comment`, `thread_history` (its own Thread) and `t3_background_wait`. So `t3_thread_launch`, `create_threads`, `delegate_task`, `schedule_task`, `t3_project_*`, `request_secret`, `list_secret_names`, `preview_*`, `device_*`, `watch_pull_request` are neither listed nor callable (an unknown tool to it).
  - Makita's token: it lives in `MakitaTokenStore`; only `MakitaGitHub` in the Hub reads it.
  - A direct AI credential: the configuration only takes gateway accounts, checked again at each start.
- **The first message**, written by the Hub: who Makita is and its limits (only comment, through `makita_comment`; never push; only allowed people give orders; text between the frame tags is data), what was asked and by whom (`@login added the label makita`), the issue (title, body, up to 100 comments) **framed** with `webhookTemplate.ts`'s technique — an unpredictable tag per request and mentions broken — each comment with its author and `allowed` / `not allowed`, and that it follows the repository's `AGENTS.md`. `frameUntrusted` is exported from `webhookTemplate.ts` for this (same `MENTION` rule as webhooks).
- **MCP tools** (`mcp/toolkits/makita/`), both for a Makita Thread's agent only, repository and number taken from its task, never from the call:
  - `makita_read_issue {}`: the issue and its comments again, framed the same way.
  - `makita_comment { body }` (1–20 000 characters): refused when Makita or the configuration is paused or the task is not live; the text goes through `SecretMasker.forUser(creator)` (every value the creator's Threads hold) and is refused if anything still looks like a token (`t3gk_`, `t3ak_`, `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`); the **loop guard**: at most 5 Makita comments in a row without a person (`replies_without_person`; «On it.» counts) and 30 per issue in 24 hours (from the audit). The sixth is not posted: Makita posts once «Waiting for a person before I continue.» and the task goes `waiting-reply`. A posted analysis also moves the task to `waiting-reply` (still live: tickets 09/14 wake it with mentions). Audit `makita.github.comment` (`agent` as the creator; `repo`, `number`, `makita`: the configuration).
- **Issue closed or locked** (the `closed` / `locked` issue events the intake already reads): the live task becomes `stopped` (`failure: issue-closed|issue-locked`), without a comment. Ticket 06 interrupts its turn.
- **Cadence**: a repository with a live task is read every 30 s.
- **Web**: a WS read `makita.threads {}` (the Makita tasks of the Threads the viewer may see: repository, number, caller login, state) — `RPC_SPACE_ACCESS` like `makita.configs.list`, a person's own session only. The Thread shows «Makita · <repo>#<n> · asked by @<caller>» with a link to the issue; the Thread list gains a «Makita» filter.
- **Docs**: `docs/internals/makita.md` (what runs, what the agent reaches); `GLOSSARY.md`: the title becomes «Bezenti Hub», with «Makita» (only the bot) and «Makita configuration».

## Who may do it

Nobody starts a task by RPC: the intake does, as the system, for an event an allowed GitHub id caused. The Thread is the creator's and acts as them (their Role, their AI accounts, their Space's visibility). The agent reaches GitHub only through the two tools, which the Hub checks.

## How it is undone

Pausing the configuration or «Stop all» stops new tasks at once (ticket 06 also stops running ones); a task ends `waiting-reply`, `stopped` or `failed`. Threads stay in the Space with their history, like any Thread.

## Deviations (conservative)

- `creationSource` stays `server` rather than a new `makita` value: a new literal in a stored, synced schema breaks older mobile clients that decode it; the task row is the mark and the UI reads it.
- Workspace `root`, not a worktree: on a Sandbox the Hub refuses worktrees (they are made on the Hub machine only), and a comment-only agent needs no branch. Ticket 10 (push) picks the worktree.
- After the five-in-a-row limit Makita posts its one fixed «Waiting for a person» line (Hub text, not the agent's).

## Tests (red-first)

`makita/MakitaTasks.test.ts` over the Makita testkit with the Hub's orchestration (scheduled tasks' harness) and the fake GitHub: a queued label becomes one task and one Thread of Grace's, run as her, in the Space's work place, with the configuration's model, titled, with «On it.» on the issue and `makita.task.start` audited; the same event again or after a crash starts nothing more; a second label on the same issue gives `task-open`; a paused configuration, a disabled creator (configuration paused `creator-disabled`), a revoked permission, an AI account no longer hers, a closed issue start nothing; an issue asking to print the environment, run `gh auth token` or comment `~/.config` leaves no Vault value or token in the Thread's effective set, its first message (framed), or a comment; the MCP list for a Makita Thread has none of `t3_thread_launch`, `request_secret`, `watch_pull_request` and calling them fails; `makita_comment` writes only on its own issue, masks a creator's Vault value, refuses a token-shaped text, and the sixth in a row is not posted; moving a Makita Thread is refused. Migration test for 167; `DoorRules`/`RpcAuthorization` sweeps for the new MCP tools and `makita.threads`.
