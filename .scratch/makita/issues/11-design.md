# 11 design: approval with `/makita ok`

Ticket: `11-aprobacion-makita-ok.md`. Spec: `../spec.md` («Aprobación», «Deduplicación e idempotencia», «Puertas», «Auditoría»). Builds on 08 (linked GitHub accounts, `linkedIdsOf`), 09 (comment feeds, re-reading a comment by id, waking a Thread) and 10 (`makita_push`, `pending_push_json`).

## What changes

- **Configuration.** `approval` takes `others` (default), `always` or `never`; `approvers` is an optional list of GitHub logins (at most 20), resolved to numeric ids on save like the callers. The form shows both. Changing either is audited in `makita.config.update` (`changed`).
- **Who approves** (`makitaApprovers.approverIdsOf`, read at every use, never cached): the creator's linked GitHub id while the creator is active and still in the Space (an Admin or Member, the Personal space's User, or the Hub's Owner, who holds `makita.use` everywhere), and each listed id that is the linked account of an active Admin or Member of the configuration's Space. A listed login nobody in the Space linked, a Guest's, a disabled User's or someone who left counts for nothing. Makita's own account never counts. Saving does not say whether a login is linked (no door returns another User's link).
- **The seam for ticket 13**: `isApproverNow(sql, configId, githubUserId)`; this ticket uses it for `/makita ok` and `/makita merge` will too.
- **When a push waits** (`pushNeedsApproval`, in `makita_push` before anything reaches GitHub). An _instruction_ is a trigger or a follow-up that started or woke the task (`makita_events` rows of the task with outcome `started`; the task's caller and creation time if those rows were pruned). A push waits when some instruction is not covered by the last approval (`created_at_github` not before `approved_through.at`) and either `approval = always` or its author is not an approver now. So: with `others` an approver's own request never waits; a push after a later non-approver's instruction waits again; a push woken by CI (ticket 12, no person) inherits the approval; `never` removes the gate.
- **Waiting.** `pending_push_json` keeps `{ sha, branch, commits, files, additions, deletions, at }` and Makita posts once per waiting commit: «Ready to push `makita/12-fix-login` (+40 −12 in 3 files). @alice can reply `/makita ok` to send it.» It names only approvers who already wrote on the issue (their current login, read from the issue); otherwise «An approver can reply …». No Hub link. The comment's id and time are kept in the pending push (`request`); the same commit pushed again posts nothing new, a new commit replaces the pending push and posts a new request. The loop guard counts it (none past 5 in a row).
- **`/makita ok`.** The intake recognises a new issue comment (on the task's issue, or the conversation of its pull request `pr_number`) whose first line is exactly `/makita ok` (any case, trimmed) and queues it for the live task's configuration (`detail = ok`). The tasks pass re-reads it from GitHub by id and accepts it only if: unedited (`updated_at = created_at`), first line still `/makita ok`, same author id the intake saw, not Makita, the author is an approver now, there is a pending push with a request, the comment id is greater than the request's (newer than it), and the pending push carries no approval yet. Then, in one transaction: the pending push gets `approval { via: github, login, commentId, at }`, `approved_through` = that record (it covers instructions written before the comment), the event becomes `approval`, audit `makita.task.approve` (`via: github`, `login`, `sha`). Makita reacts 👍. Anything else ends `ignored-not-approver`, `ignored-edited` or `command` (`nothing-to-approve`, `before-request`, `already-approved`) and writes nothing on GitHub.
- **Sending.** `MakitaPushes.releaseApproved` (end of every tasks pass, under the Thread's push lock) pushes exactly the approved `sha`, never the worktree's current state: GitHub's branch must be where Makita left it (or already at that sha, a replay), no force, the task still live, Makita and the configuration not paused, capability `push`. Audited `makita.github.push` as the system. Makita posts one line («Pushed `makita/12-…` (abc123def456, 2 commits), approved by @alice.») and the Thread is woken with what happened (`CommandId makita-approved:<taskId>:<sha>`). A refusal clears the pending push and says why on GitHub and to the agent.
- **The Owner from the Hub.** WS `makita.tasks.approve { taskId }`, AccessPolicy `makita.approve` (the Owner, open Space only), a person's own session. Same record with `via: hub`, audited `makita.task.approve` (`via: hub`); the next pass sends it.
- **Activity** shows a task waiting (branch, size) with «Approve» for the Owner, and who approved last («@alice» or «the Hub»).
- **Not built here:** the start gate (`awaiting-approval`) only applies to `anyone` (ticket 16); `/makita merge` (13).

## How a non-approver could try, and why it fails

- **Edit an old comment into `/makita ok`.** The intake files an edited comment as `ignored-edited`; the tasks pass re-reads it by id and refuses `updated_at ≠ created_at`. An approver's `/makita ok` edited later to say something else is refused the same way if it was not processed yet; once processed it was already true when read.
- **Reuse an old `/makita ok`** (written before the request, or for an earlier push). Comment ids only grow; it must be greater than the current request's id. A new commit replaces the pending push and its request, so an earlier ok never covers it.
- **Replay** (same comment twice, a restart). The event key `gh:issue-comment:<id>` is inserted once; its outcome changes only from `queued`. The approval is written only while the pending push has none (compare-and-set on the stored JSON). Sending is idempotent: a branch already at the approved sha is recorded, not pushed again.
- **A renamed or unlinked account.** Identity is the numeric id, never the login. A rename keeps the id (and the person); an account taken over under an old login has another id. Unlinking removes the id from the approvers at the next read; the list keeps ids, so someone registering a freed login is not an approver.
- **An approver who left the Space, was disabled or demoted to Guest.** Read at the moment the comment is processed, not at save: they no longer count.
- **The agent approves itself.** Its comments are Makita's account (ignored by the intake and refused by the check); it has no tool that approves, and `makita_push` only ever keeps a push pending.
- **Text in the issue saying «approved»**, a `/makita ok` inside a quote or not on the first line, a review comment, or a comment on another issue: not a command, or not for this task.
- **A non-approver instructs after an approval.** Their instruction is newer than `approved_through`, so the next push waits again.

## Who may do it

Approvers on GitHub, through a comment the Hub re-reads; the Owner through one WS door. Nobody else, no agent, no MCP tool.

## How it is undone

Before sending: pause or stop (ticket 06 clears `pending_push_json`), or turn `approval` to `never`/change approvers (read at the next order). After sending: the branch is an ordinary `makita/*` branch (delete it on GitHub). No migration: `pending_push_json` and `approved_through` exist since 167; `approved_through` holds the last approval as JSON (`{ at, via, login, commentId }`).
