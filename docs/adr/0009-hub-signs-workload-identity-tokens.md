# The Hub signs workload identity tokens for Threads

The Hub is an OpenID Connect issuer for the work it runs. For a Thread whose effective set includes a workload identity entry, it signs a short-lived token naming the Installation, User, Space, Project, Thread and Active environment, for the audience that entry allows, and delivers it as a Secret file it refreshes before it expires. Kubernetes API servers, OpenBao or Vault JWT auth, AWS, Google Cloud and Azure federation trust the Hub's issuer instead of a secret stored for the Space, and their own logs show which User and Thread acted. The Hub publishes its discovery document and public keys at its public URL; the signing keys never leave its encrypted store.

## Considered Options

- **A long-lived credential per Space in a Vault** (a service-account token, cloud keys): simplest, but a leak lasts until someone rotates it by hand, and every action looks like the Space, not the User.
- **Dynamic secrets only** (ADR 0008): short-lived and per Thread, but they need a Secret provider for every target and still hand out a credential the provider, not the target, attributes.
- **The Organization's identity provider** (Keycloak client credentials per Space): its tokens cannot name a Thread or a Project, and a client secret is still stored for each Space.
- **SPIFFE/SPIRE**: workload identity built for this, but one more always-on system with node attestation that a single Hub on a VPS does not need.
- **The Hub as issuer** (chosen): it already decides who runs what where, so its claims are the authoritative ones; verifiers need only its public keys.

## Consequences

- A new trust root: whoever holds the signing key can act as any Thread toward every system that trusts the Hub. The key is generated by the Hub, sealed with the master key, rotated with an overlap during which both keys verify, and never exported, not even in the master-key backup flow.
- `/.well-known/openid-configuration` and the JWKS are public and must answer without a sign-in, also behind an access proxy in front of the Hub (Cloudflare Access in bezenti's deployment), and verifiers must reach them or be given a discovery URL inside their network.
- Tokens are bearer tokens while they live: short lifetimes (minutes), one audience per token, and a `jti` in the Hub's audit log.
- The Hub's session tokens stay as they are (HMAC); only workload identity uses asymmetric keys.
